# 再起動後の source_mismatch：原因と改善案

2026-10-31（Asia/Tokyo）。利用者のエラー画像を受けた読み取り調査。修復・再構築・本体起動・設定変更・テスト実行は行っていない。

## 結論

通常版 `.runtime` と現在のソースの不一致により、起動前の検査が停止している。現在のディスクを起動guardへ渡しても `MORI_STARTUP_SOURCE_MISMATCH` を返し、画像と同じ原因を確認した。再起動により生じたファイル破損の証拠ではなく、前回作業後の未反映ソースが次の起動時に検出された状態。

| 読み取り項目 | 結果 |
| --- | --- |
| 通常runtimeの構築日時 | 2026-10-25 12:12:19 UTC（21:12:19 JST） |
| runtime ready／固定upstream一致 | true／true |
| 通常runtimeの構築指紋 | `0325c2eaf470023558fe940d5f5cd896863c06f881862a71dc6bf72b398923fd` |
| 現在のソース指紋 | `2577d6907b56003bd4ea486db1850c4521f1544fe119e5c20e540708b58df01e` |

変更7件はcontent-script／conversation-binding／outbox／service-worker／transport／browser-bridge-server／browser-session-store。未追加31件には計測module・解析器・計測テスト等がある。テストだけの差と判断してguardを緩められる状態ではない。

詳細な読み取り結果: `reports/startup-source-mismatch-20261031.json`。通常workerのSHA256は以前からの `cb14a3e00ef3f0699ae6fdd1ad6b58e2b0154c73d201f1cc912f401e52972f85` を保持している。これは当該ファイルが保持された証拠であり、runtime全体の破損検査を完了した意味ではない。

## 発生の仕組みと作業上の問題

1. `scripts/prepare-runtime.js:248` はupstream lock・patch・**overlay全体**を指紋へ含める。テストと計測専用ファイルも対象。
2. `inspectRuntimeSource` は指紋に加え、overlay各ファイルと生成build情報を現在のソースへ照合する。
3. `bootstrap/main.js` はその検査に成功してから本体をspawnする。`scripts/startup-guard.js` が不一致を `source_mismatch` へ分類する。
4. 前回の計測作業は別stageだけを再構築し、通常 `.runtime` を保持した。しかし起動時の比較対象となるoverlayは更新していた。
5. 起動済みプロセスではこの起動前検査を繰り返さない。次回起動で不一致が表面化した。

前回の「通常runtimeを保持した」という説明はファイル保持については正しかったが、**更新後のソースを使う次回起動も可能であることを確保できていなかった**。起動契約と計測開発の分離が不足し、作業完了時の確認でも見落とした。

今回のエラー経路は本体spawn前であり、本体のデータ初期化処理へ進んでいない。利用者の保存データそのものは今回読み取っていないため、全データの正常性を検査済みとはしない。Windowsの自動起動登録やElectron起動後の動作も未確認。

## 改善案

### P0：通常起動を復旧する

現在のソースから通常runtimeを標準手順で再構築する。依存のpackage／lockが一致する場合は既存の `npm run rebuild`（`node scripts/setup.js --reuse-dependencies`）を使い、不一致なら `setup-windows.bat` の通常setupを使う。

既存のtransactional setupで所有stageへ構築・Electron／assetsを確認してから `.runtime` を入れ替える。稼働プロセスやファイルロックがあれば、実行パスを照合して原因を整理する。保存データ・ペアリング・未読・通常版の拡張IDを保持する。build情報だけを書き換える方法は使わず、実ファイルとの整合性を維持する。

復旧確認は、ディスク整合→通常起動→同じ起動入口のログインモード→実Windows再起動の順に行う。Chromeとの接続復帰と監視復帰は別に確認する。再構築や既存回帰の成功だけで、PC再起動後の受入を完了にしない。

### P1：常用環境と開発ソースを分離する

最初の候補は**常用用checkoutと計測開発用worktreeを分ける**こと。常用のoverlay／patchを開発作業で変えなければ、現在の厳格な起動検査をそのまま維持できる。通常版と計測版の保存先・接続・拡張IDの分離も維持する。既存の自動起動の参照先変更は必要な場合だけ明示的に行い、OS側で無効化された登録を復活させない。

将来、常用runtimeを編集可能なcheckoutから独立させる場合は、構築時に固定した成果物manifest、build ID、依存・Electron・製品identityを検証する別設計にする。比較対象を現在の作業ツリーから固定成果物へ移す際は、manifest自身の信頼根拠、未承認成果物の拒否、変更・欠落の検出、切替／rollbackを定義して独立レビューする。起動チェックを単純に外す案とはしない。

### P1：作業終了時に「次回起動可能」を確認する

計測キット準備やsource更新の最後に、通常runtimeの起動整合状態も読み取りで記録する。表示を次のように分ける。

- 通常runtimeのファイルを保持した。
- 現在のソースと通常runtimeは一致／不一致。
- 次回の通常起動は検査通過見込み／保留／未確認。

不一致のまま「既存の利用可能なruntimeを保持」と一括表示しない。開発変更で通常起動が保留になった場合、復旧手順と構築指紋の違いをその作業の終了時に報告する。

### P2：エラー表示を原因に合わせる

今回の `source_mismatch` では「本体の起動を確認できませんでした」だけでなく、**「ソース更新が本体へ未反映のため起動を保留しています」**と説明する。不一致の内訳、構築日時、診断ファイルの保存先、修復手順を表示する。原因不明の欠落・読取失敗まで更新未反映と断定しない。

起動時に依存取得やruntime更新を自動実行せず、通常のsetupと起動の所有者・排他を維持する。

## 実装後の検証計画

- source変更後の停止、現在ソースでの再構築後の通過、生成情報／実ファイルの欠落・改変の拒否。
- 通常用checkoutと計測用worktreeの分離、計測テストだけの変更、製品ファイル変更を区別した起動条件。
- setup／起動の競合、ファイルロック、構築失敗時の旧成果物保持。旧成果物保持と現ソースでの起動可否を分けて判定。
- 本体と拡張のbuild identity、接続・通知保持。保存データを消さずに復旧すること。
- 実Windowsで手動起動・ログイン起動・PC再起動。OSで自動起動を無効にしたケースも保持。

今回は分析と提案まで。修復の実行、起動登録の変更、回帰／再起動の試験結果は含めない。
