# Gmail HUD 実装案

2026-11-04 時点の実装方針と配布前条件。対象は Mori Desk のブラウザー中心の通常起動であり、Gmail 連携は CLI セッションやブラウザー観測の状態から独立させる。個人検証用 Cloud プロジェクトで A/B の同期と Chrome の実在リンクを確認済み。本番プロジェクトと社内配布の受入は未完了。実測は [個人検証記録](../../reports/gmail-personal-live-test-20261104-ja.md)、配布条件は [導入チェック](gmail-hud-deployment-ja.md) を参照。

## 目的と表示仕様

社員が Gmail の受信トレイを都度開かずに、優先送信者からの新着とその他の未読を見つけ、必要なメールへ移動できるようにする。

メール用のペット付随カードを追加する。既存の「今日の予定」カードと同じ幅・高さ、ドラッグ移動、角丸、明暗配色、見出し、状態と最終取得時刻、スクロールする一覧、フッターの「更新」「設定」「閉じる」を踏襲する。既存の AI セッション HUD の状態・未確認通知件数には混ぜない。

一覧は次の二つのセクションに分ける。

1. **優先送信者**: 設定済みの送信元アドレスから届いた新着メール。通常の未読一覧との重複表示はしない。優先メールは Gmail で既読になっても、HUD の「一覧から除外」で明示的に外すまでは残す。この操作は当該 PC の表示だけに効き、Gmail の既読化や業務上の対応完了を意味しない。
2. **その他の未読**: Gmail の `UNREAD` が付いた受信メール。ただし優先送信者に一致するものを除く。Gmail で既読になったら次の同期で外す。

各セクション内は Gmail メッセージの `internalDate` を基準に新しい順に並べる。画面に表示する「受信時刻」と「最終取得時刻」は別の値とする。優先判定は `From` の表示名ではなく解析したメールアドレスの完全一致とし、大文字小文字を正規化する。登録にないドメイン全体や似た表示名へは拡張しない。この一致は送信者本人の認証を保証しないため、UI に「認証済み」などの印は付けず、メール本文のリンクを自動で開かない。複数アカウントを将来扱う場合に備え、アカウント ID を各行の識別子へ含める。優先セクションで未除外の行は時間経過だけで消さず、表示枠を超えた分もスクロールまたは件数付きの折りたたみで参照可能にする。

一覧の行には送信者、件名、受信時刻、未読表示を出す。カレンダーと同じ `<details>` 方式で行を開き、送信先、概要、本文、Gmail の URL、「Gmail で開く」「URL をコピー」を表示する。本文は行を開いたときだけ `messages.get(format=full)` で取得し、プレーンテキストに変換する。応答サイズと表示文字数を制限し、添付ファイルは取得しない。HTML メールを埋め込み表示せず、外部画像やスクリプトも読み込まない。本文取得失敗時もヘッダーとリンクは表示する。行を開くこと自体は Gmail の既読化も「一覧から除外」もしない。

初回接続時は受信トレイの未読を `messages.list(q="in:inbox is:unread")` で100件取得し、各件のメタデータを順次取得する。次ページがある場合は「未読の一部は未取得」と常時表示し、「さらに読み込む」で追加する。初回上限外の未読が差分同期だけでは現れないことを仕様に明記する。接続前から既読になっている優先メールは遡って追加しない。接続後の新着は優先送信者であれば既読化後も「一覧から除外」まで保持する。カード内はスクロールで閲覧する。

## 更新方式

**初期実装はデスクトップ側の5分間隔の差分同期を推奨する。** Gmail の公式資料も、インストールされた端末への更新取得にはポーリング方式を案内している。Gmail の変更通知を受けるために、ローカル HTTP サーバーを Gmail のフック受け口として公開しない。

1. OAuth 連携直後に現在の `historyId` を控え、範囲を限定した初期同期を行う。その間の変更を控えた ID から差分取得してから、処理済みの `historyId` を保存する。初期取得中の新着も取りこぼさない。
2. 起動時および5分ごとに `history.list(startHistoryId=保存値)` を呼ぶ。復帰時・オンライン復帰時は次のタイマーで検知する。
3. 変更があったメッセージ ID のみ `messages.get(format=metadata)` で取得し、追加・既読化・ラベル変更・削除を反映する。履歴の全ページと必要なメッセージの保存が成功してからカーソルを進める。
4. 「更新」ボタンは同じ差分同期処理を即座に起動する。処理中はボタンを無効化し、連打は一回へまとめる。最後の実行から60秒未満なら API を呼ばず、次に押せる時刻を示す。手動更新が成功したら次の自動更新をその時刻から数える。
5. 更新に失敗したら古い行を残し、「以前の取得結果」「最終取得時刻」「再試行時刻」を表示する。401 はアクセストークンを一度更新して再試行し、更新トークンが失効した場合に再連携を求める。429/一時障害は `Retry-After` と指数バックオフに従う。古い `historyId` による404では未読を再取得し、以前の優先行を保持する。既読になっていた優先メールの欠落は復旧しきれないため、部分同期と明示する。

Push 通知は、実測で5分の遅延が業務上足りない場合の第2段階とする。Gmail `watch` → Cloud Pub/Sub → 組織の受け口 → デスクトップへの変化通知、という経路が必要になる。通知に本文・送信者は含まれず、受けた後に `history.list` を呼ぶ。通知の遅延・欠落があるため、Push 導入後も周期的な差分同期を残す。`watch` は期限前に更新する。

## API 枠と認証

Gmail API の枠はリクエスト回数でなく quota units で計測する。2026-11-03 の公式表では `history.list` は2、`messages.list` は5、`messages.get` は20（`format=full` は60）、`watch` は100 units。5分ごとの `history.list` が毎回1ページで、メールの追加取得も手動更新もない場合は、1アカウントにつき 2 × 12 × 24 = **576 units/日**。初回100件のメタデータ取得は約2,000 units で、1日に新着20件を取得するなら別途400 units が加わる。実際に API 呼び出しを試みた分をローカルの利用量台帳へ計上し、同一 PC・同一アカウントの並行取得を抑える。Gmail には毎分の units 枠とは別にユーザー単位の同時実行制限もあるため、初期取得は少数並列で進め、バッチを使う場合も50件以下とする。複数社員で共有するプロジェクト全体の利用量はローカル台帳だけでは把握できないため、Cloud 側の利用量・エラー率・課金閾値のアラートと、端末間で同期しないランダムな更新時刻のずれを組み合わせる。公式表にはプロジェクトあたり1日8,000万 units の課金閾値も記載されている。社員数、平均新着件数、初回同期、手動更新を含む利用量試算を配布前の必須条件にする。実際の枠・請求状況は組織の Cloud プロジェクトで確認する。

本文表示には `gmail.readonly` を使う。カレンダーのOAuth許可やトークンへ暗黙に権限を追加せず、Gmail 専用の同意画面・保存領域を設ける。更新トークン、必要最小限のヘッダー、ローカルの除外状態、`historyId` は OS の `safeStorage` で暗号化して保存する。アクセストークンと本文はメモリのみで扱い、本文をディスクへ保存しない。カードを閉じるかアカウントを切り替えたら本文を破棄し、連携解除時は Gmail 専用の認証・キャッシュを削除する。保護された保存が使えない状態では連携を開始しない。ログ・診断・IPC エラーにはメールアドレス、件名、本文、URLを出さず、状態種別と件数のみ残す。Gmail の `gmail.readonly` は制限付きスコープである。組織所有の Cloud プロジェクトで Internal OAuth として社員のみに配布する場合と、外部利用者へ配布する場合では審査条件が異なるため、配布形態を確定して管理者・Google の要件を確認する。将来サーバーで制限付きデータを保存・中継する構成に変える場合はセキュリティ評価の要件も再確認する。

Gmail の URL は API から直接渡される値ではなく、Gmail 画面の深いリンク形式も API 契約では保証されない。連携時に `getProfile.emailAddress` を保存し、固定の `mail.google.com` ドメイン、接続アカウント、検証済みのメッセージ/スレッド ID から表示用 URL を生成する。IPC から渡された URL をそのまま開かず、現在の保存行を ID で引き直して生成する。複数 Google アカウントを開いた Chrome で正しいメールへ遷移する実機試験を必須とし、誤ったメールボックスへ移る場合はアカウント名を示して Gmail 内検索への代替導線を出す。差出人や本文に書かれた URL をこのボタンの遷移先として使わない。

## ソース構成

- `overlay/src/mori-mail-core.js`: アドレス正規化、セクション分類、時刻順、表示上限、URL の検証。
- `overlay/src/mori-mail-api.js`: OAuth、Gmail API、ページング、応答サイズ制限、エラー分類。
- `overlay/src/mori-mail-store.js`: Gmail 専用の暗号化された認証・設定・キャッシュ・`historyId`・利用量台帳。
- `overlay/src/mori-mail-runtime.js`: 初期同期、差分同期、手動更新、失敗時の保持、再同期。
- `overlay/src/mori-mail-window.js`、`preload-mori-mail.js`、HTML/CSS/renderer: カレンダーカードに準拠する画面と、送信元・メッセージ ID を検証する IPC。
- `overlay/src/mori-browser-window.js`: カードの起動・配置・終了時の結線。ただしブラウザーセッションストアへメールメタデータを入れない。
- 既存の upstream ファイル変更が必要な場合は `.runtime/` だけを編集せず `patches/mori.patch` へ反映する。新規ファイルは `overlay/` に置く。

設定画面では Gmail の連携・解除、優先送信者アドレスの追加と削除、最終同期と再連携の状態を扱う。更新ボタンの状態はカレンダーと同様、取得中・待機・利用枠停止・認証切れを区別する。

## 完了条件と検証

1. 優先送信者の新着が上段、その他の未読が下段に一度だけ現れ、各段が受信時刻順になる。Gmail 既読化と HUD の「一覧から除外」がそれぞれ定義どおりに動く。500件超の初期未読は部分表示と追加取得の導線が残る。
2. 「更新」がクールダウン後に差分同期を起動し、連打・自動更新との競合で二重取得しない。失敗時は既存の行と `historyId` を失わない。
3. 行の開閉、本文の遅延取得、URL表示・コピー・Gmail で開く操作が、カレンダーのカードに準拠する。外部本文は DOM にテキストとして挿入する。
4. 429、401、期限切れ `historyId`、途中ページ失敗、OS の暗号化不可、オフライン、アカウント切替、偽装された `From`、巨大な本文をテストする。API 呼び出し数・units・同時実行数を検証する。
5. Node 24.18+ で root の `npm test` の個別アサーションと完了状態を確認する。ソース変更後は通常 runtime を再構築し、runtime 保持と次回起動のソース整合を別々に報告する。Google アカウント、Windows/macOS、複数アカウントの実機確認は合成テストと区別する。
