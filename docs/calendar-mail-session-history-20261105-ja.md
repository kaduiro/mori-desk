## 実装の構成

この節は、2026-11-05 時点で確認した実装を説明する。個人検証用設定と配布バイナリはソースブランチに含まない。

| 領域 | 主なソース | 内容 |
| --- | --- | --- |
| Calendar | `overlay/src/mori-calendar-{api,core,runtime,store,window}.js` と HTML/CSS/renderer、setup 画面 | Desktop OAuth、複数カレンダーの選択、当日予定の取得・表示、説明文と安全な URL、手動更新、100要求の端末台帳 |
| Gmail | `overlay/src/mori-mail-{api,core,runtime,store,window}.js` と HTML/CSS/renderer | 単一アカウントの連携、初回未読取得と5分の履歴差分、優先送信者の分類、本文の遅延取得、手動更新、端末内 quota units 台帳 |
| 共通 HUD | `overlay/src/mori-hud-layout.js`、各 preload と window、`patches/mori.patch` のメニュー・起動連携 | 独立した起動時表示、手動再表示、タスクバー復帰、画面内への配置、文字倍率、サイズ選択、自由寸法と右下ハンドルの保存 |
| 将来設計 | `docs/hud/` と `docs/mail/` のローカル設計文書 | 複数 Gmail アカウントを扱う場合は不透明な `accountId` で認証・キャッシュ・行 ID・IPC・リンクを分離する。現行は1アカウント・1 Mail HUD |

生成される `.runtime/` と `.upstream/` は最終ソースではなく、Git に入れない。個人検証用 OAuth 設定、トークン、予定・メールのキャッシュも配布・コミットしない。

### 同期と保護の判断

- Gmail の初期取得は件数を区切り、未取得ページがあれば画面に示す。以後は `historyId` から差分を取得し、必要なメッセージだけを読む。自動確認は5分間隔、手動の「更新」は同じ同期経路を使う。失敗時に既存の行や履歴位置を誤って確定しない。
- 端末内の Gmail 制限は20,000 units／24時間と2,500 units／分。利用者ごとの Google 側の枠や法人プロジェクト全体の合計を、この端末の台帳だけで保証しない。初回100件の取得、本文詳細、手動更新を含む利用量を法人側で実測する。
- Calendar と Gmail の OAuth 権限と保存領域を分離する。Gmail は `gmail.readonly` のみを要求する。OS の安全な保存が使えない場合は連携を進めず、本文はディスクに保存しない。表示に使う外部文字列はテキストとして扱い、IPC で渡された任意 URL をそのまま開かない。
- Gmail の深いリンクは Gmail API の保証する URL ではない。アカウントを指定して生成しても、対象アカウントが未ログインなら別アカウントへ切り替わる可能性がある。社内配布の合否は Chrome での未ログイン試験とプロフィール一致確認に依存する。

## 残る作業と開始条件

1. **個人環境の受入**: Calendar の説明文・会議参加 URL を持つ実予定、HUD のタスクバー復帰と OS ログイン起動、DND・オフライン・日付切替を確認する。Mail の「自由」ハンドル操作も Windows 実機で確認する。
2. **Chrome のリンク安全性**: 独立した検証用 Chrome プロファイルで、対象アカウントだけが未ログイン、アクティブアカウント変更、ログイン順逆転を試す。別アカウントのメールへ誤遷移する場合は、法人向けの深いリンクと URL コピーを無効化し、アカウントを明示する手動確認導線へ切り替える。
3. **法人の所有と承認**: 組織の Workspace／Cloud 管理者、課金担当、対象部門と先行利用者を決め、組織所有の本番プロジェクトを作る。Calendar と Gmail の API・Desktop OAuth、Internal 利用条件、必要最小限のスコープ、管理者のアプリ制御を実画面で確認する。
4. **本番の枠と費用**: 実プロジェクトの Quotas & System Limits、API Metrics、Cloud Billing の紐付け、請求先、予算通知、403/429 と使用量を確認する。公開値や個人プロジェクトの枠を本番の実効値として扱わない。
5. **法人先行試験と配布判定**: 承認済みの1～2人で7～14日を目安に同期・表示・再起動・Chrome リンクを試す。実ビルド、署名、OS 信頼、更新・復旧も確認してから社内配布を判断する。現時点で本番プロジェクト、管理者承認、法人先行試験、配布バイナリはない。

## 独立ソースブランチへの引き渡し

`codex/calendar-mail-source` は固定した基点 `cf1162b` から別の作業ツリーに作成した。`patches/mori.patch` は固定上流との差分として再生成し、Calendar・Gmail の起動とメニューに必要な変更を加えた。`mori-browser-window.js` とブラウザーパネルの共有ファイルは Mail/Calendar の導線だけを移し、別件のブラウザー通知処理を含めない。個人検証データ、生成 `.runtime/`、別件の監視用ソースはこのブランチのコミット対象外とする。

この隔離先では固定上流から通常 runtime を再構築できた。初回の配置は Windows の一時的なファイルロックで失敗したが、既存ファイルを壊さず再試行で成功した。その後のパッチ整理時は npm ミラーの名前解決に失敗したため、同一の依存ロックを照合して既存のインストール済み依存をコピーし、Electron と生成素材を検証してから runtime を入れ替えた。Calendar・Gmail とブラウザーパネルの個別試験52件は全件成功。ローカル通信を許可した環境でルートの `npm test` は425件中423成功・失敗0・スキップ1・todo1、終了コード0。`npm run doctor` で隔離先のソース入力と構築済みファイルの一致を確認した。これは元の常用作業ツリーで行った Windows 実機試験とは別の証拠であり、隔離先バイナリを配布・署名した証拠ではない。基点の Chrome 拡張は `0.1.8` で、別件の監視作業ツリーの `0.1.15` と混同しない。
