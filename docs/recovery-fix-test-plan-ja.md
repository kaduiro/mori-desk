# 監視復旧の修正案と、利用全体を確認するテスト計画

策定日: 2026-10-21（日本時間）

対象版: 本体 0.1.3-preview.1 / 拡張 0.1.6

## 1. 結論と到達目標

既知の3不具合を修正する。合わせて「診断を押したから復旧した」を自動復旧の成功に含める試験を分離し、利用者が導入から会話へ戻るまでの一連の操作を別の基準で検証する。

完成の対象は「拡張の接続済み表示」ではなく、次の利用である。

1. BATで導入し、実際に更新した本体と拡張を起動できる。
2. ChatGPT / Claudeを複数タブで使い、各行の会話名・送信済み依頼・生成状態・未確認通知・移動先が同じ会話を指す。
3. 別アプリや別タブで作業中も必要な通知に気付ける。更新・一時的な切断・休止からの復帰で、文章や通知を失わず、原則としてF5・再ペアリング・診断操作を繰り返さず利用を継続できる。
4. 確認できない状態は確認中と表示し、別の会話や終了通知で補わない。
5. 対象のタブへ正常に戻った場合だけ、操作開始時に指定した通知を確認済みにする。

1タブで同時観測するのは現在の会話のみである。前に表示した会話をバックグラウンドで監視し続ける機能や、AI回答の正常終了を保証する機能は今回の範囲に含めない。

**差分の修正完了、統合試験の合格、Windowsでの限定試用、社員への配布は別の判断とする。必須の実機確認が未実施なら、その段階は未確認であり合格ではない。**

計画レビューの最終判断: A/CとBの保留・失効・再登録の骨組みは実装着手可。Bのprovider別自動承認は、実画面の帰属根拠を調査・査読してから有効化する。既知3不具合を含む現在のPRはマージ保留を維持する。

## 2. 今回の独立レビューの方法

3人の新しいエージェントへ、親の修正アルゴリズムや既存fixtureを先に渡さず、異なる入口から合否基準を導くよう依頼した。

| 担当 | 初期に使う根拠 | 先に固定する判定基準 | 初期に使わないもの |
|---|---|---|---|
| 実行順序・故障の反証 | 製品コード、Chrome公式APIの契約 | 遅延・停止・失効・遷移後にも成立する不変条件 | 既存テストfixture、先行再現スクリプト、親の修正案 |
| 利用者視点の受入 | 公開仕様、利用目標 | 別管理の会話台帳と実UI・本体記録の一致 | 製品ソース、既存テスト、内部healthy/acceptedを正解とする判定 |
| 業務・配布の判断 | 利用目標、公開手順 | 段階ごとの必要証拠、未確認の扱い、対象OSと配布経路 | 既存fixture、親の案、テスト件数だけの合格判定 |

各担当が初期基準を先に提出し、その後この具体案を渡して反証レビューした。第1案は3担当とも追加修正を要求した。指摘を反映した第2案を固定済みの基準で再レビューし、起動時の確認契約を補った第3案の限定差分も実行境界・配布判断の担当が確認した。仕様上の成功条件は共有するが、テスト入力・真値・期待結果の生成まで同じ実装からコピーしない。基準間の矛盾は記録して解決し、単純な多数決では閉じない。

今後の実装担当は、独立fixture・会話台帳・受入判定プログラムを自分の実装に合わせて変更しない。期待結果を変える必要があれば、仕様の変更として理由と対象ケースをレビューする。

3担当は独立した人間の実利用者ではなく、同じ系統のAIエージェントである。入口を分けたことだけで判断の相関がなくなるとは扱わない。公式API契約、実Chromeの挙動、別管理の会話台帳、対象OSでの実操作を、異なる根拠として追加する。

## 3. 修正A: タブ取得の遅延を保存障害にしない

### 3.1 対象と設計

対象: overlay/extensions/browser-bridge/service-worker.js の initialize、requestFreshObservations、reconcileTabs、エラー分類。

現在は初期化が監視復旧まで待つため、追加したtabs.queryの1,500msタイムアウトがstorage_failedへ伝播する。次のように分離する。

- 必須初期化: storageのアクセス制限、認証情報と保存データの検証、outboxとsessionの整合性回復、必要な永続化、transport生成。ここで実際の保存障害があれば従来通り停止する。
- 任意の復旧処理: タブ列挙、現文書の確認、監視プログラムの起動。必須初期化完了後に開始し、この処理の完了を必須初期化のPromiseに含めない。
- タブ列挙の既知の失敗・タイムアウト: 「監視確認を延期」として次回の自動試行へ進める。資格情報を削除せず、保存障害と表示せず、再接続操作を塞がない。
- 保存・鍵・データ整合性の異常: 致命的な障害として維持する。reconcile内のcloseTab後のcommitもこの分類であり、一括catchで握りつぶさない。
- 未分類の実装例外やアラーム設定失敗: 専用の固定カテゴリにする。storage_failedへ誤変換したり、無条件に成功として返したりしない。

新しいobserverの登録が必須初期化を待っても、必須初期化がそのobserverの復旧を待つ循環を作らない。既存のHMAC・保存後ACKの順序は変更しない。

### 3.2 初期化を分離する際の追加条件

タブ一覧の結果が古くなっている可能性も扱う。query開始時の対象recordと世代を記録し、完了後に増えた新規タブを古い一覧にないという理由で閉じない。遅れて到着した失効済み試行の結果は採用しない。

取得失敗を空配列へ置き換えない。また、host permissionがないためURL条件付きqueryに現れないタブを「閉じた」と判定しない。閉鎖はonRemovedなどの根拠、または同じrecordの現在の存在・routeを再確認できた場合に限る。根拠不足は観測不明のまま保持し、未確認通知を消さない。

### 3.3 必須テスト

| ID | 入力・故障 | 合格条件 |
|---|---|---|
| A1 | queryが期限直前、期限と同時、期限直後、1.7秒、5秒で返る／返らない | 保存正常なら保存障害にしない。期限超過した処理だけを失効させる |
| A2 | 起動直後のqueryだけ失敗し、次回は成功 | F5・診断・再接続・再ペアリングなしで対応タブの観測が本体へ戻る |
| A3 | queryが同期throw、Promise reject、遅延resolve | 各経路が同じ非致命分類になり、未処理例外でworkerを止めない |
| A4 | query開始後に新しいタブBの観測が保存され、古い結果にはAしかない | Bを閉鎖・履歴化せず、Bの未読と移動先を保持 |
| A5 | query失敗またはhost permission保留 | 空一覧・閉鎖として確定せず、許可の範囲を超えて回復しない |
| A6 | local/sessionの読込・書込・資格情報検証・outbox回復が本当に失敗 | fail closedを維持し、接続成功・通知ACKを返さない |
| A7 | query結果到着前に停止・解除・worker再起動 | 古い試行の結果で監視を再開せず、解除した状態を書き戻さない |
| A8 | 初期化とobserver登録・onReady・onInstalledが重なる | 循環待ちがなく、復旧試行と観測を重複起動しない |

時間の境界はテスト側の時計で正確に扱う試験と、実ブラウザで実際に遅延を入れる試験を分ける。タイムアウトを単に延ばすだけの修正は採用しない。

## 4. 修正B: 復旧したobserverが旧会話のDOMを採用しない

### 4.1 URL一致と会話内容の一致を分ける

対象: observer-recovery.js、content-script.js、conversation-metadata.js、provider adapter、workerの観測受理。coordinator/storeは承認された観測だけを受け取る境界を検証する。

documentId・frameId・URLは実行対象を確かめる情報であり、同一document内の中央会話DOMがその会話に切り替わった証拠ではない。固定時間の待機、DOMの静止、旧ノードの消失、同じ文面がなくなったこと、sidebarでBが選択されたことだけで中央の依頼・停止ボタンをBへ帰属させない。

新しい監視は次の段階を経る。

| 段階 | 許可すること | 許可しないこと |
|---|---|---|
| 起動待ち | 対象document・worker・設定の確認 | 通常の生成・抜粋の送信と保存 |
| 会話との対応を確認中 | 読み取りだけの構造確認。根拠があるexact-routeの会話名は別扱いにできる | 中央DOMの依頼抜粋・running・terminal・新しい未読の作成・既存通知の確認ACK |
| 対応確認済み | 同じ有効な試行と会話に属する観測の採用 | 別route/旧試行/失効済み文書の観測 |
| 失効・停止 | 既存履歴と未読の保持、理由表示 | 遅れて動いた旧プログラムによる再開 |

会話名、依頼抜粋、生成状態にはそれぞれの根拠を必要とする。Bのsidebarリンクから得たタイトルを許可できても、それを中央のstopや依頼の証明に流用しない。

### 4.2 二段階で起動・受理する

まず、登録時の文書同一性確認（bootstrap）と、利用者が会話へ戻ったことを確認するfocus成功応答を分ける。現行のobserver-recovery.currentIdentityとworkerのcheckCurrentDocumentはmori.focus.checkを再利用している。ここへ帰属gateを加えるだけでは、「許可前の登録確認が、許可済みの応答を要求する」という循環になる。

bootstrap応答は、未承認でも文書/observer/routeの必要最小限の同一性だけを返せる。通常の観測・抜粋・通知ACKを許可する応答ではない。既存の各呼出し用途を棚卸しし、登録・同一性確認用とfocus用を別messageまたは厳密な用途別schemaへ分ける。bootstrap成功を利用者のfocus成功へ流用しない。帰属の構造確認は保留状態でも読み取り専用で進められ、その結果とworkerが検証した対象が揃ってから許可する。

1. workerが復旧試行の識別子と対象tab/document/route/設定世代を作成し、有効な試行を管理する。
2. 注入したプログラムは保留状態で起動する。最初のobserveから通常のデータを送信・保存しない。初期登録はURL等の必要な識別情報と固定カテゴリに限定する。
3. 対象の確認と会話DOMの帰属確認が揃ってから、workerがそのobserverに観測の採用を許可する。
4. workerは観測の受理直前にも試行・document・route・有効設定を照合する。注入後の検査だけに依存しない。停止・解除との確定順は下記の共通変更キューで定義する。
5. URL変更、文書交代、停止、解除、期限超過、workerの新しい起動で旧試行を失効させる。古い注入が後から実行されても、通常観測を採用できない。
6. worker再起動時は有効なobserverの再登録を行う。無効になった試行IDを復元して承認済みにしない。既存observerを重複起動しない。workerの許可世代とobserverの連続観測期間は別に管理する。

すべての観測入口に同じ条件を適用する。定期観測、初回observe、mori.observe.now、mori.health.check、visibilitychange、pageshow、復帰後の再送のどれからも未承認の観測を通さない。force指定は帰属確認を省略する権限ではない。

観測の採用、設定世代の変更、ペアリング解除による保存状態の変更には、単一の変更キューまたは同等の直列順序を使う。設計上の境界は次の通りとする。

- 停止・解除の要求を受けたら、新規の採用開始を直ちに止め、未着手の旧試行を失効させる。設定変更の成功応答はまだ返さない。
- 変更キュー内で最後の照合を通り、永続化を開始した観測は、その後に到着した停止要求より前の操作として決着させる。非同期書込みを後から取り消せたと仮定しない。
- 先行操作が終わってから設定・資格情報の変更を永続化し、停止・解除の成功を返す。未着手の観測や、失効後に検査から戻った観測は採用しない。共通キューの中でobserverの再登録応答を待つ循環は作らない。
- pauseより前に確定した未確認通知は保持する。unpairでは既存の解除仕様に従って拡張の資格情報・配送待ち状態を処理するが、本体へ保存済みの通知を一括消去しない。解除成功後に旧試行が状態を書き戻したり、旧ペアリング宛てに再送したりしない。
- outbox書込み成功後にsession書込みが失敗する場合も、既存のdurable receipt回復と保存障害停止を維持する。停止への対応を理由に保存済みreceiptを失わせない。

試行IDはページ側の自己申告だけで有効とせず、workerが管理した対象と一致させる。内部messageの変更は厳密なallowlistに追加し、既存のdesktop wireに新しい自由形式データを追加しない。旧形式の新規観測を無条件に通す互換処理は置かず、更新時の承認を取り直す。既存の保存済み通知は4.4の移行境界に従う。

focusについても、現行のmori.focus.checkとworkerのvalidateFocusが会話の帰属確認を必要とする。現世代のpageInstanceIdであっても、URL=B・中央DOM=Aの未確認中は成功を返さない。現在の「移動して通知を確認する」操作は、対象の物理タブ・会話・有効な帰属を移動の前後で確認できた場合だけ成功にする。途中で実際のタブ移動が起きても、最終確認が失敗したら未読を残す。ACKを伴わない単なるタブ移動を提供するなら別操作として定義し、今回の成功応答へ混ぜない。

executeScriptのタイムアウトは呼出し先の実行を取り消すものとして扱わない。後から動き出す場合を明示的に試験する。また、復旧処理を初期化Promiseから分離して、登録を待つ側と注入を待つ側が循環しないようにする。

### 4.3 会話DOMの帰属を確かめる方法は、実画面を調べて確定する

ここは設計上の未確定点であり、存在未確認のdata属性を発明して実装してはいけない。

- providerごとに、現在会話のIDと表示中の会話root/生成controlを結び付ける、実際に取得可能な構造的な根拠を調査する。
- その根拠がroute変更に先行更新される／旧会話を指す／存在しない画面を独立fixtureで試す。rootの識別属性だけ新しくなり中身が旧会話のまま、という反例も含める。
- 連続して正常に観測していた同じobserverの情報は補助になるが、失効・新規注入時に履歴があると仮定しない。
- storage.sessionは拡張reload/update/disableやブラウザ再起動で消える。保存された旧routeがない復旧を必須ケースにする。
- 依頼の本文、下書き、AI回答、Cookie、内部API応答、フレームワークの非公開データを広く収集する案は採用しない。対象範囲は現行の認可済み表示情報と構造に限定する。

**十分な根拠が取得できない画面では、会話との対応を確認中と表示し、状態と抜粋を保留する。これは誤通知防止の成功であり、自動復旧・業務受入の成功ではない。**

対応を確定できないまま無期限に止まるなら、当該画面の自動復旧は未達とする。対応可能な画面範囲の縮小、取得方式の再検討、利用者による対象画面の確認などを別途判断する。ページを自動でF5したり、根拠の弱い待ち時間で成功へ繰り上げたりしない。現在のChatGPT/Claudeの実画面で帰属根拠が成立することが、修正Bの実装完了・受入判断の前提である。

調査の成果物は、provider・画面種類・言語ごとの「会話IDを示す構造」「その構造が結び付く本文領域」「生成controlとの対応」「更新順がずれる反例」「確認日・対象版」「成立/不成立/未確認」を記した表とする。現時点ではChatGPT/Claudeの自動承認に使える根拠は未確定であり、B8の入力仕様も確定待ちである。保留・失効の骨組みは実装できるが、自動承認の有効化はこの調査結果を独立レビューしてから行う。成立しない結果も残し、fixtureへ都合のよい属性を加えて解決した扱いにしない。

### 4.4 通知のルール

承認直後に既存の非生成画面が見えても終了通知は作らない。承認された同じ会話・同じ連続観測期間で生成開始と停止を確認できた場合だけ、従来の「生成停止を観測した」という結果を作る。次の3種類の空白を区別する。

| 空白 | 引き継げる根拠 | 必要な結果 |
|---|---|---|
| workerだけが停止し、同じobserverが同じ会話を継続観測 | 受理済み開始、同じobserver/会話/生成の識別、継続した観測 | 新しいworker許可を取り直してもcontrollerを無条件resetしない。同じ生成の停止通知を1件届け、別turn・別行を作らない |
| observerそのものが失効・交換され、空白中に停止 | 以前のrunningと復帰時のidleしかない | 停止を補完しない。既存未読を保持し、次の確実な新規生成を待つ |
| 観測と保存は完了し、desktopへの配送だけが止まる | durable receipt、配送イベントの識別 | 再配送と重複排除を維持し、通知を失わせず二重加算しない |

連続性を証明できない場合はobserverの空白として扱う。workerの許可世代が変わったという理由だけで、証明できる連続性を捨てない。新規生成は以前の未読を消さず、focus成功はクリック開始時に捕捉した通知だけを確認済みにし、処理中に到着した後発通知を残す。

旧版で既に誤帰属したreceiptが保存されていた場合、新しいgateだけでは正当な旧通知と区別・修復できない。誤帰属防止は新しい受理条件を通る観測について主張し、旧receiptのreplayを新たに帰属確認済みの観測として数えない。正当な既存未読を含む一括削除は行わない。更新試験は、正当な旧receiptの保持と、疑義ある旧receiptを含む移行の限界を別に記録する。

### 4.5 必須テスト

| ID | 独立した入力シナリオ | 合格条件 |
|---|---|---|
| B1 | A生成→observer失効→URLだけB→AのDOM残留→再注入→Bの既存idle画面 | Aの依頼・生成・終了をBへ一度も保存/表示しない。Bの新規通知0、旧未読は不変 |
| B2 | 旧AのDOMが0ms、100ms、2秒、10秒、期限超過まで残る／別ノードへ複製される | 待ち時間・ノード差だけで承認されない |
| B3 | 新Bのsidebar名だけ先に表示／root属性だけBへ更新 | 証明できる名前だけを許可し、中央の依頼・生成・通知を混同しない |
| B4 | A→B→A、同URLの文書交代、同会話の2タブ | 各物理タブと現在文書を分離し、旧世代の観測・focus ACKを拒否 |
| B5 | 4秒で注入待機がtimeout→停止/解除/遷移→注入が遅れて実行 | 旧注入からの観測がcommitも通知もされない |
| B6 | 注入直後、後段検査前に初回observeが走る | 登録・帰属確認前のrunning/metadata/terminalが保存されない |
| B7 | storage.sessionが残るworker再起動と、消える拡張更新/再読込 | 両方を扱い、旧route履歴がなくても誤帰属しない |
| B8 | 実画面調査で根拠と入力仕様を確定したBが表示され、その後Bで新規生成→停止 | Bの正しい名前/最新送信/状態/通知1件/移動先が一致。永久unknown・空欄・古い抜粋で安全テストだけ通る実装を落とす |
| B9 | sidebar閉鎖、権限保留、凍結、破棄、未対応UI | 許可/根拠不足を明示し、復旧成功や完了を捏造しない |

| B11 | gate直後・outbox書込み完了直後・session書込み完了前にpause/unpair | 外部ラッチで定めた確定順どおりに採用/拒否。先行receiptを保全し、解除成功後の書戻し0 |
| B12 | Bの開始を受理済み→workerだけ停止→同じobserverの再登録→停止を観測 | 同じ生成に正しい通知1件、不要なturn/行増加0 |
| B13 | observer自身を失効→空白中に生成停止→新observerでidle | 推測による終了通知0。B12との正負の差を検査 |
| B14 | 未帰属中にhealth、observe.now、visibilitychange、pageshow、再送をそれぞれ実行 | どの入口も帰属確認を迂回せず、抜粋・生成・通知・focus ACKを採用しない |
| B15 | 実Chromeの専用profileで実際の拡張reload/update | isolated worldの交代、session消去、旧観測拒否を実環境で確認。runtime.idのmock書換えだけで代用しない |

| B17 | 正当な対象ページで未承認状態からbootstrap→帰属確認→許可→初回観測 | 診断や事前許可の差込みなしで最初の正当な観測が届く。bootstrap中のfocus/ACKは失敗し、既存未読を保持。許可条件の循環待ち0 |

拡張の一意性は、probeの応答が1件という結果だけでは判定しない。計測付きの隔離試験でobserverインスタンス・タイマー・送信元の重複を確認し、通常の受入では実採用・通知の重複がないことも見る。計測がworker寿命に影響する場合は、自然停止の証拠には使わない。最低対応Chrome版と導入先の版を記録し、任意のAPIフィールド（例: frozen）が存在しない場合も永続保留や例外にしない。

## 5. 修正C: 履歴で編集中のカードを親ごと隠さない

対象: overlay/src/mori-browser-renderer.js のrefresh/renderSessionsと必要な表示用状態。

- 行の論理上の所属、実際のDOM配置、編集中状態を分ける。
- 編集・IME変換中のcardを移動しない場合、そのcardを含むhistory親も表示したままにする。
- 並べ替え・移動を確定した後に、実際の子cardと編集保持の有無を見て空のhistoryを隠す。論理historyRowsの件数だけでは決めない。
- 表示件数が先にcurrentへ変わる場合は、利用者がカードを見つけられる表示を維持する。フォーカスを強制移動してIMEを解決しない。
- 確定・保存・blur後は一度だけ正しい所属へ移す。保存中に追加した文字や未読は変更しない。

| ID | 操作 | 合格条件 |
|---|---|---|
| C1 | 唯一の履歴行の表示名を変換中→同じbrowserRunで再接続 | 入力欄と親が可視、フォーカスと未確定文字を維持。カードの二重表示なし |
| C2 | 履歴が複数、currentが複数、一部だけ再接続 | 編集していない行は正しく移動、対象以外の表示名・通知は不変 |
| C3 | current→history→currentを入力中に繰り返す | 編集ノードと入力を維持し、確定後に正しい一覧へ一度だけ移動 |
| C4 | IME候補選択/取消、変換確定Enter、その後の保存操作、blur | 候補の取消と表示名編集全体の取消を混同しない。変換確定Enterで意図せず保存しない。操作どおりの文字・保存先・フォーカス、保存失敗後の再編集 |
| C5 | 非同期保存中の再接続＋新しい入力 | 古い保存結果で新しい入力を上書きしない |

DOM fixtureのcompositionstartを発火する試験は状態遷移の証拠に限定する。実Windows＋日本語IMEで、入力欄、変換候補、未確定文字、確定後の保存結果を別途確認する。macOSは別の実機結果が必要である。

現行にない「Escで編集全体を取り消す」機能をこの修正へ暗黙に追加しない。空欄保存による自動名への復帰、同じ会話の別タブへの名前共有、別profile/別providerへの非共有も既存の仕様と照合する。

## 6. 同じモック・期待値への依存を減らす試験構成

| 層 | 試験対象 | 独立性の作り方 | この層だけでは言えないこと |
|---|---|---|---|
| 仕様の状態表 | 会話・物理タブ・生成・通知・フォーカスの関係 | 実装を読まず作った会話台帳と期待イベント数を先に固定 | Chromeで実行されるか |
| 制御できる故障試験 | 実worker/content/storeとAPI境界 | 新規の小さなAPI代替を作り、同期throw/遅延/順序変更/未完了を外から指定。既存helperをコピーしない | 本物のChrome API・IME・provider DOMで同じか |
| 実Chrome＋独立合成ページ | 拡張注入、更新、worker再起動、遷移、本文帰属、通知配送 | 別担当が実装のselector定数をimportせず作る複数のHTML/SPA遷移。テスト台帳はページ外に置き、拡張に真値を渡さない | 実サイトの未取得構造やUI差分への対応 |
| 実Chrome＋実Electron | 表示・通知・正しいタブへのfocus・保存まで | 実HMAC/loopback/本体storeを通し、画面と結果を会話台帳と照合。Chrome内部acceptedを正解にしない | 利用者OSの鍵保存・IMEが別環境でも動くか |
| 対象OS＋実サービス | BAT初回導入/翌回起動/更新、実ChatGPT/Claude、日本語IME、休止復帰、背景継続利用 | 専用の非機密会話を使い、利用手順から最後の確認まで実施 | 別OS・別provider UI・未確認の特殊機能まで完成したか |

共有してよいのは公開された業務上の条件と外部プロトコルであり、製品のreducerやmetadata readerから期待値を計算しない。共通fixtureは既存の回帰検知用に残すが、独立受入の唯一の証拠にはしない。

合成ページは「根拠あり」「根拠なし」「根拠が先に変わり本文が古い」「新しいノードだが旧本文」の別系統を持つ。複数のfixtureが同じHTML生成関数の見た目違いになる構成を避ける。実サービス由来の構造的事実は確認した版と画面範囲を記録する。

会話台帳の必須項目は、試験/step、物理タブの外部別名、browser起動区分、provider、routeの会話、中央本文の会話、名前の会話、送信する識別文字列、未送信の識別文字列、予定した生成操作、既存通知の対象集合、クリックが捕捉する集合、期待移動先とする。期待関係とシナリオは先に固定してhashを残し、実際の送信・生成の外部時刻や到着結果は別の実測欄へ追記する。実行結果から期待値を後付けしない。通知は件数に加え、どの外部イベントに対応する通知が残ったかを照合する。製品のopaque IDを観測証拠との対応表へ記録しても、そのIDだけから正解を作らない。

## 7. 自動復旧を、修復する検査から分離する

自動復旧の判定区間では、テストdriver・診断画面・外部の待機helperからmori.options.health、mori.observe.now、手動retry、再ペアリング、監視切替、ページ再読み込みを呼ばない。結果を見るために対象タブを前面化・再表示することも避ける。製品自身の通常のalarm/onUpdated等が行うprobe・再登録・mori.observe.nowは、自動復旧の機能なので許可する。禁止するのは検査が介入して修復する経路であり、自動トリガー自体ではない。

観測は本体側の画面・到着イベント・保存済み通知と、独立したページ台帳で行う。worker側へのポーリングはworkerを起こす可能性があるため、自然な停止/再起動を試す区間では使わない。workerのDevTools/debuggerも閉じる。検査接続が対象workerをattachして生存を維持する場合、その区間は自然停止の試験に使わない。Chrome公式もinspect中はworkerが稼働を続けると説明している。実行する操作と、状態を見る操作を別のチャンネルにする。

自然停止は、workerが実際に停止し、別の起動として再開した証拠を必要とする。workerを起こさないブラウザ側lifecycle記録等を使い、観測方法が寿命へ与える影響も確認する。本体の切断だけでworker停止と断定しない。証拠を取れなければUNKNOWNとし、強制停止・拡張更新の成功で代用しない。必要な停止を発生させていない試行は有効な試験数に含めない。

自動復旧は「以前のrunningが残っている」だけでは合格にしない。障害解除後の新しい実観測の到着と、会話台帳に一致するHUD/記録を先に確定する。その後に、新規生成・停止・HUDクリックで対象タブへ戻る操作を行う。この順序により、クリックや前面化が復旧を助けた結果を自動成功に含めない。Chrome smokeの現在のhealth待機ループは、この独立な完了判定に置き換える。診断で直る経路は、結果固定後の原因調査または初期状態を戻した別試行にする。

### 仮の時間・回数基準

以下をこの計画の初期受入目標とする。Chromeの保証や測定済み性能ではない。変更するなら実行前に理由を記録して基準を改版し、失敗後に期限を延ばして同じ試行を合格へ変えない。

- 正常時の名前・最新送信・状態・新規通知の表示反映は、外部で対応する画面変化を確認してから5秒以内を仮目標とする。
- 自動復旧は45秒を唯一の合格期限にする。権限・本体・ブラウザが稼働し、台帳上で対応する会話の画面が成立して外部障害が解除された時刻をt0とする。製品のbinding成立/healthy/connectedの時刻へ起点を後送りしない。
- 通常の前面タブと背景タブの両方で、全必須タブの正しい新規観測が期限内に戻ることを要求する。ChatGPT前面/Claude背面、逆配置、両方背面で別タブ・別アプリが前面、別ウィンドウ、Chrome最小化を別ケースにする。背景へ移っても時計を止めない。
- 45秒を超えた時点で不合格を固定する。120秒までは受動的に証拠を集め、45〜120秒の復旧はFAIL-late、120秒でも復旧しなければFAIL-no-recoveryと記録する。120秒は第二の合格期限ではない。
- 凍結・破棄・OSスリープ等で外部的に実行不能な期間は別分類とし、その事実を製品のunknown以外の証拠で記録する。解除後を別途測り、利用者の全待ち時間も併記する。理由を確認できない停止を都合よく分母から除かない。
- 必須の決定的遷移は各1回以上、タイミングを変える実Chromeの重要ケースは各10回を初期基準にする。ランダム試験はseedと失敗順序を保存し、具体的な残余リスクが見つかった場合に追加する。
- Windows限定試用前に2時間の通し作業と3回のスリープ/復帰を行う。社員配布前には対象OSごとに通常勤務1日相当（初期目標8時間）の背景利用、終業と翌回起動を追加する。常時手動操作や業務会話の録画を要求せず、非機密タスクを間に置く。これは長期ゼロ障害の保証ではない。
- 新しい受理条件を通る観測の誤会話への文字列・生成・通知、既存未読の意図しない消去、同じ物理タブの同じ生成の重複通知、入力喪失は試行中0件を必須とする。同じ会話を開いた別タブの通知を、会話IDだけで重複と判定しない。

帰属根拠が得られず確認中のままのケースは、安全性では合格し得るが、自動復旧率の成功に数えない。安全性と有用性を別々に集計する。

## 8. テストが誤った修正を検出できることも確認する

隔離した試験用コピーにだけ、次の故障を意図的に入れる。製品ブランチへは残さない。

| 故障版 | 必ず失敗すべき検査 |
|---|---|
| query timeoutをstorage_failedへ戻す | A1/A2が、保存障害表示・復帰不能を検出 |
| 全例外をcatchして成功扱いにする | A6が、本物の保存障害時のACK/接続成功を検出 |
| query失敗を空配列として扱う | A4/A5が、不要な閉鎖・履歴移動を検出 |
| 帰属gateを省略する／excerptだけ抑止してrunningを許す | B1が、誤った生成または偽通知を検出 |
| 待ち時間だけで帰属済みにする | B2/B3が、古いDOMの採用を検出 |
| 注入後の検査だけに戻す／失効IDを受理する | B5/B6が、遅延注入または初回観測のcommitを検出 |
| 自動の復旧トリガーを無効化し、手動診断だけ残す | 診断なし試験が期限内に失敗し、手動試験の成功と区別される |
| すべてunknownのまま返す | B8と通し受入が、正しい観測・通知へ戻らないことを検出 |
| 論理history件数だけで親を隠す | C1が、可視性・配置の不一致を検出 |
| focus判定だけ帰属gateを外す | B10/U14が、現世代だが未帰属の会話の誤ACKを検出 |
| 設定変更を別queueへ戻し、保存前のifだけにする | B11が、解除後の旧状態の書戻し・順序違反を検出 |
| worker再登録のたびにcontrollerをresetする | B12が、正当な継続生成の通知欠落を検出 |
| 以前running＋復帰時idleから終了を補完する | B13が、観測空白中の偽通知を検出 |
| force/health経路だけgateを迂回する | B14が、別入口からの未帰属観測の採用を検出 |
| 再送の二重加算／再接続で未読を初期化／クリック後の全未読を消す | U10/U12/U13が、通知の対象集合の不一致を検出 |
| healthyだけ返してHUD/実記録を更新しない／名前や抜粋を空欄固定にする | U02/U03/U08が、識別情報と新規観測の不一致を検出 |
| 前面化イベントでだけ復旧させる | U21が、通常の背景タブの期限超過を検出 |
| bootstrapにも承認済みfocus応答を要求する | B17が、初回登録の循環待ちを検出。bootstrap応答の有無と最初の正当な観測を別々に確認 |

有効な故障版の検査には「原版が同条件で合格」「意図した故障が実際に発動」「狙った要件で不合格」の3点を必要とする。起動クラッシュや無関係なtimeoutは感度の証明にならない。自動復旧だけを無効にする場合も、権限・ペアリング・通信は正常に保つ。利用者が停止した設定を無視させる検査にはしない。これらの故障版で試験が成功してしまう場合、その試験は対応する要件の合格根拠に使わない。

対象provider・OS・UI言語・画面種類（最初は通常テキスト会話）を実行前に固定する。失敗後に範囲を狭める場合も元のFAIL/UNKNOWNを残し、別の製品範囲変更として判断する。現在対象のChatGPT/Claude両方、日本語IME、Windows通し利用を任意ケースへ変えて合格させない。手順開始時から終了時まで会話台帳を保ち、最後の画面だけで判定しない。

業務受入では誤通知の有無だけでなく、必要な通知が実際に出ること、識別できること、戻る先が正しいこと、手動介入の回数を記録する。確認中が続いて仕事に使えない状態を安全性の合格で覆わない。

## 10. 証拠と結果の残し方

各結果に、試験ID、合否基準の版、実行日時、実行者、対象HEAD、dirty有無、本体成果物のhash、実Chromeが読み込んだ拡張のパス/版/hash、OS/Chrome/Electron版、providerと画面範囲、故障条件、seed、PASS/FAIL/UNKNOWN/NOT-RUNを記録する。

加えて、会話台帳hash、故障の発動証拠、外部t0、反映/復旧時刻、実行した手動介入とその時刻、通知の対象集合、観測手段とworker寿命への影響、原版と故障版の対応を残す。安全性・期限内復旧・業務継続の結果は別欄とする。B8は帰属仕様確定待ち、実Windows/macOSの新しい通し受入は未実行として管理する。

overlay側と.runtime側で別の拡張を読み込めるため、ソースHEADだけで検証対象を同一と見なさない。必須UNKNOWN/NOT-RUNは、該当段階の合格を止める。失敗後にretryやhealthで直った結果で元の失敗を上書きしない。

証拠は専用の非機密会話と合成文字列を使う。テスト台帳のA/B等の識別子はテスト側だけで持つ。製品の診断へURL・会話本文・認証情報・任意の例外文を追加しない。OS暗号化のテストダブルを使った結果と実OSの鍵保存結果も分ける。

## 11. 実装・確認の順序

1. 独立基準とこの計画をレビューし、帰属確認方法の実画面調査を先行する。根拠が成立しない場合は対応範囲の判断を残し、Bの完成を宣言しない。
2. 既知3件の失敗を示す試験と、診断なし自動復旧の失敗判定を先に用意する。既存fixtureとは別の判定を含める。
3. Aの初期化/故障分類/古いquery結果を修正し、保存失敗が依然停止することまで確認する。
4. Bの保留起動、採用許可、失効、provider別の帰属確認を修正する。初回送信と遅延注入を重点確認する。
5. Cの親領域とcard移動を修正し、実Windows IMEで確認する。
6. 再構築、既存回帰、独立統合、故障版の検出、Windowsの通し受入を順に実施する。
7. 証拠が揃った段階だけを合格とする。社員配布はMac/配布経路/業務シナリオの結果が揃ってから判断する。
