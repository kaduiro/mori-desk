## 1. 新たに指定された契約

1. 通信の非同期処理と利用者の停止・接続解除・接続置換が競合しても、古い処理が「接続済み」や後続通信を復活させない。
2. setupが保存する入力fingerprint（pin、patch、overlay）と起動時の現在入力を照合する。更新されたcheckoutに対してruntimeが古い場合は起動を拒否し、再構築を案内する。
3. 読取り専用のローカルdoctorで、checkout/runtime/指定した拡張フォルダーのディスク上の版・hashを照合する。実行中Chromeの確認は別であり、このdoctorの成功で確認済みにしない。

## 2. transportの独立した時系列と期待値

テスト側の台帳で旧接続をC1、置換後をC2とする。暗号演算、受信イベント、送信、onReady/状態通知、timer/retryを別々に記録する。Promiseを外部ラッチで止め、ユーザー操作の前後を制御する。製品内部のepochやconnectedを期待値の生成に使わない。

「停止後に通信しない」は、停止要求より前に開始され相手へ送信済みのbyteを取り消すという意味ではない。停止後に古い処理の再開を理由として新しい送信・接続成功・復旧timer・外部callbackを開始しない、という境界である。保存を開始済みのdurable receipt等の先行処理は既存の確定順に従い保全する。

| ID | 外部操作順 | 必要な結果 |
|---|---|---|
| T01 | C1の接続/handshake開始→非同期処理待ち→利用者停止→C1処理成功 | 接続済み/onReady/新送信/heartbeat/retryを復活させない |
| T02 | C1の認証処理待ち→ペアリング解除/資格置換→C1成功 | 旧資格で通信/接続を再開しない。新資格や解除済み設定を書き戻さない |
| T03 | C1の送信署名待ち→C2接続→C1署名完了 | C1用のbyteをC2へ送らない。C1由来の失敗でC2を閉じない |
| T04 | C1受信の検証待ち→停止/C2へ置換→C1検証成功 | 旧受信を新しい接続のイベント/ACK/readyとしてcallbackしない |
| T05 | C1のready処理待ち→C2が正常接続→C1処理成功 | readyや状態変更を二重発火せず、C2の状態をC1で上書きしない |
| T06 | C2が正常接続後にC1のclose/error/遅延timerが発火 | C2のsocket/heartbeat/認証状態を壊さず、余分な再接続を開始しない |
| T07 | 非同期の署名/検証が成功するケースとrejectするケースを、停止/置換の各境界で実施 | どちらも旧世代の副作用0。未処理rejectionで現行通信を壊さない |
| T08 | C1処理開始→停止→明示の再開でC2→C1遅延完了 | 明示再開はC2として動作し、旧C1の復活と区別される。単なるstopped booleanの戻りだけでC1を有効化しない |
| T09 | onReady等のcallback中に利用者停止/置換を起こす | callback後に続くflush/heartbeat等も現行権限を再確認する。callback実行前の1回確認だけに依存しない |
| T10 | 現行C2で正常handshake→通常送受信→正当な再接続 | 正常機能が失われない。全Promiseを無視する修正/永久未接続を合格にしない |
| T11 | 正常に送信済みの同receiptを再接続後に再配送 | ACK/保存/重複排除の既存契約を維持し、R1/R2対象集合を失わない |
| T12 | 複数回のstop、同時に到着するclose/error、明示停止後のtimer発火 | 停止は冪等で、旧通信の再開0。新しい明示connectが必要な場合のみ再開できる |

実装が実際に持つ非同期境界を読んだ後、上表に対応する入口を選ぶ。存在しないAPIや挙動を要求するためのテストは作らない。検出力確認は、実装内のguardを1箇所外した隔離コピー等により、正常版PASS→対応する古い送信/ready/現行接続破壊のassertion FAILを確認する。構文エラーや無関係なtimeoutは数えない。

## 3. 起動前fingerprint照合

| ID | 外部から作る状態 | 必要な結果 |
|---|---|---|
| S01 | 同じpin/patch/overlayから完成したruntimeと一致する入力 | 通常起動が可能。単に全起動を拒否する修正は不合格 |
| S02 | setup後にpinだけ、patchだけ、overlayの内容だけをそれぞれ変更 | 古いruntimeの本体を起動する前に拒否し、再構築が必要と分かる |
| S03 | overlayへのファイル追加、削除、同名別byte。semverは据置 | 対象集合と内容変化を検出する。versionやmtimeだけで判定しない |
| S04 | 保存済みfingerprint欠落/破損/不正型、必要入力の読取り失敗 | 無条件に現行とみなさず、検査不能または再構築必要とする。生の任意例外文を公開診断へ流さない |
| S05 | ルートの説明文書だけ変更、列挙順やOSパス区切りだけ異なる | 実際の入力が同一なら不要な製品差異を作らない。fingerprintの再現性を保つ |
| S06 | 起動を拒否する条件でruntime/データが存在 | 拒否は旧runtime・利用者データ・設定・未読を削除しない。自動の再ペアリングも行わない |
| S07 | fingerprintは一致するがruntime内の生成ファイルを後から変更 | 起動前入力チェックの検出範囲を正確に説明する。チェックが検出しない場合に『全runtime byte完全性を証明』とは言わない |
| S08 | 異常な入力/呼出しで修復コマンドを表示 | 本文やpathをshellとして実行しない。ユーザー指示なしの権限/ポリシー迂回なし |

inputFingerprintはsetup入力の一致という範囲で評価する。実行中Chromeの版、runtimeの後変更、Electron依存の全byte、OSの互換性を自動的に証明するものではない。これらを検出すると主張する機能がある場合は、その実測を別途求める。

## 4. 読取り専用doctor

| ID | 条件・反例 | 必要な結果 |
|---|---|---|
| L01 | checkout、runtime、指定した拡張フォルダーのcode byteが同じ | 定義した対象範囲のdisk一致を示す。Chrome実行中は未確認を維持する |
| L02 | semverは同じ、拡張の実行ファイル1 byteだけ異なる | hash/対象集合で不一致を検出する |
| L03 | runtimeは旧版、指定フォルダーは新overlay、または逆 | どの組合せが不一致かを識別できる。3者の一部一致を全一致にしない |
| L04 | 拡張フォルダー未指定/不存在、manifest不正、必要ファイル欠落 | 未指定/検査不能/不一致を区別し、成功扱いしない |
| L05 | 入力fingerprintは一致、runtime拡張ファイルだけ改変 | stampだけで実ファイル一致としない。diskファイルをhashする機能の検出対象になる |
| L06 | 別フォルダーで全code byte同一、パスのみ異なる | code同一を示せるがChromeがそのフォルダーを読込中とは推測しない |
| L07 | 実行中Chromeが未接続/未照会、またはdisk更新後も旧workerが動作 | disk PASSとは別の『実行中未確認』を表示・機械結果に残す |
| L08 | doctorを一致/不一致/異常入力の各条件で実行 | setup、runtime再生成、依存導入、ペアリング、DB更新、ブラウザ操作、ネットワーク送信を起こさない |
| L09 | コード配置近傍に会話データ/秘密の合成sentinelを置く | 既知のコード入力に限定し、診断出力に無関係ファイル/タイトル/資格/任意例外を混ぜない |
| L10 | 人間向け表示とJSON等の機械用結果、成功/失敗exitがある | 表示・判定・exitの意味が矛盾しない。unconfirmedの実ロードを『healthy』に丸めない |

実体確認がない実ロードをUNKNOWNとすることは正しい成果である。今回のdoctorはU23全体（実更新後の通し利用）を完了させるものではない。ローカルdiskの候補が明らかになった時点で、実際にロードしたパス/版/対象環境の実機記録へつなげる。

## 5. 結果の留保

transportの正負境界試験、起動前照合、disk doctorが通過しても、実providerのbindingは未確認のままである。今回候補に対する正の実Chrome/実Electron/Windows/IME/背景復旧受入が存在しない限り、旧FAIL-no-recovery・I-B8未達・限定試用NO-GOは維持する。
