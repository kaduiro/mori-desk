# 今日の予定・受信メール HUD の UX 改善と残タスク

2026-11-04 時点のソース調査。現状分析と実装案であり、この文書の作成によって HUD の動作は変更していない。実装順序と法人受入は [実行計画](calendar-mail-delivery-plan-20261104-ja.md)、本番導入条件は [Gmail 導入手順](../mail/gmail-hud-deployment-ja.md)、実機受入の残件は [残存タスク](../remaining-tasks-20261105-ja.md)を参照する。

## 原因と改善案

| 困りごと | ソースで確認できた原因・範囲 | 改善案 |
| --- | --- | --- |
| キャラクターの右クリックから Gmail HUD を開けない | `patches/mori.patch` の `src/menu.js` の2つのメニュー構築箇所には「今日の予定」だけがある。`mori-browser-window.js` の `openMail()` は既にあり、ブラウザ連携画面からは呼べる | 両メニュー箇所に「受信メール」を「今日の予定」と並べて追加し、main のメニュー context に `openMoriMail: () => moriBrowserWindow.openMail()` を渡す。未連携でも HUD を開き、連携案内へ進める。現在のブラウザ専用起動は `workGroup.splice(2)` で後続項目を消すため、固定位置の削除をやめて CLI 専用項目だけを条件追加する |
| 窓と文字が小さい | 両ウィンドウは `340×360`、`resizable: false`。`position()` と保存位置の復元も毎回 `340×360` を使う。`layout.json` は座標のみ。共通 CSS は本文12px、補足や時刻は10px | 両 HUD のサイズ変更を有効にし、幅・高さも保存。初期値を例として `400×480`、最小 `320×300` とし、画面の作業領域内に制限する。別途、両 HUD 共通の文字倍率 `100/125/150%` を設け、本文・時刻・ボタンまで拡大する。拡大時は件名を折り返し、詳細と一覧をそれぞれスクロール可能にする |
| 他の窓を押すと HUD が消え、戻しづらい | 両 HUD は `skipTaskbar: true` でタスクバーに出ない。ソースに `blur` で閉じる処理は見当たらない。自動表示分は DND・ミニモード・HUD 無効・ペット非表示を検知すると `close()` する。手動で開いた既存 Calendar 窓は `show()` のみで `focus()` しない。両 HUD は同じペットの横に幅340・高さ360で配置され、Mail だけ縦に30pxずれるため、初期状態では大部分が重なる。クリックだけで閉じたのか背面・他 HUD の下に回ったのかは未確定 | まず実機で `isVisible`、`isFocused`、`blur`、`hide`、`closed`、抑制理由を内容なしの状態ログで切り分ける。自動配置で両 HUD が重ならない位置を選ぶ。通常の HUD はタスクバーから復帰可能にし、メニューからの手動表示は `show()` と `focus()` を両方行う。自動表示だけが抑制された場合は表示意図を保持し、抑制解除後に復帰する。明示的な「×」は閉じたままとする。「常に手前」を HUD ごとに切り替えられるようにする |
| 将来の複数 Gmail アカウント | 現在は `auth.json`、`cache.json`、`settings.json` と `connectedAccount` が各1件。`disconnect()` は3ファイルを削除する。1つの HUD・1つの同期キューを前提にしている | 今は複数連携 UI を増やさない。将来の内部契約を `accountId` に紐づく認証・キャッシュ・優先送信者・非表示 ID・同期状態とし、行 ID は `(accountId, messageId)` で一意にする。OAuth 同意と解除はアカウント単位、Gmail リンクはその行を所有するアカウントから生成する。別アカウントの本文や URL を表示しない境界テストを用意する。複数 HUD は `Map<accountId, window>` に拡張可能な窓管理で扱う |

### サイズ・位置・表示状態の詳細

- `layout.json` をバージョン2へ移行し、旧バージョン1の `x/y` は維持して既定サイズを補う。幅・高さ・文字倍率は整数と範囲を検証する。モニター切替、DPI 変更、解像度縮小時は見える領域へ収める。手動配置でなければペットに追従し、サイズ変更だけでは「手動配置済み」にしない。
- 枠なし透明窓で OS の端をドラッグして変更できるか Windows 実機で確認する。操作が分かりにくければ右下にサイズ変更の目印を設ける。macOS 向けに配るなら同環境でも確認する。標準文字を14px程度、補足・時刻を12px以上とする案を起点に倍率を調整し、単純な窓拡大だけで文字の問題を解決した扱いにしない。
- `skipTaskbar: false` の採用時は Calendar と Mail の窓名・アイコンが識別できることを確認する。明示的な閉じる、抑制による一時非表示、他窓の背面化、最小化を別状態として扱う。本文は明示的な閉じる・抑制による破棄・連携解除時に消去し、復帰時に必要なら再取得する。診断にメール件名・本文・URL・送信元を記録しない。
- 自動表示は既存の DND・ミニモード・HUD 無効・ペット非表示を尊重する。手動表示は抑制中でも使える現行仕様を維持する。「常に手前」を外した場合も、タスクバーまたは右クリックメニューから一操作で戻れるようにする。

### 複数 Gmail アカウントへの準備

- 将来の保存領域は生のメールアドレスをファイル名にせず、ローカルで割り当てた不透明な `accountId` に分離する。更新トークンと最小限のキャッシュは引き続き OS の `safeStorage` で暗号化し、本文はメモリだけに置く。既存の単一アカウントからの移行は、暗号化状態・所有アカウントを検証してから行い、失敗時には元データを保持する。
- 端末全体の 24 時間 API 台帳は共有しつつ、アカウントごとの利用量と Google 側のユーザー別制限も追跡できる形にする。追加アカウント数に応じて初回取得と5分差分確認の合計が増えるため、同時接続数・同時 API 呼び出し数を制限する。
- 将来の画面はアカウントごとの HUD か、1つの HUD の切替表示かを利用者試験で決める。現段階では1件の連携・1件の HUD を維持し、複数アカウントの実装を今回の UX 修正へ混ぜない。

## 残存タスクと順序

| 優先 | 作業 | 完了条件 |
| --- | --- | --- |
| P0 | 右クリックメニューの「受信メール」追加 | キャラクターとトレイの両方の該当メニューから、未連携・連携済みで HUD を一操作で開ける。ブラウザ連携画面の既存ボタンも動く |
| P0 | HUD のサイズ・文字倍率・位置保存 | Calendar/Mail の両方で拡大、縮小、再起動後の復元、複数モニターの作業領域への収まりを確認。補足文字も読め、一覧と詳細の操作ができる |
| P0 | 「消える」現象の実機切り分けと復帰導線 | 他窓をクリックした直後の窓状態と理由を特定。通常時は閉じず、背面化してもタスクバーかメニューから一操作で復帰。DND 等の抑制解除後は意図どおり復帰し、明示的に閉じた窓は勝手に再表示しない |
| P1 | Calendar の残る実機受入 | 実予定の説明・会議 URL、ドラッグと位置保持、再起動・OS ログイン起動、DND/ミニ/オフラインを [残存タスク](../remaining-tasks-20261105-ja.md)の条件で確認 |
| P1 | Gmail のリンク・表示の追加受入 | 利用対象の Chrome で、正しいアカウントをログアウトした場合とログイン順変更を確認。Chrome で誤アカウントへ切り替わる条件では深いリンクの正確性を保証せず、アカウントを明示した安全な導線へ切り替える。設定表示中も一覧が操作可能か視覚確認する |
| P1 | 本番 Cloud・OAuth・配布 | 組織所有プロジェクト、実利用枠・課金設定、Internal と管理者承認、法人先行試験、実ビルド・署名・配布先 OS の受入を完了。個人検証用の認証情報とデータを配らない |
| P2 | 複数 Gmail アカウントの内部境界設計 | `accountId` と保存・同期・IPC・URL の契約、旧単一アカウントからの移行、API 台帳の共有方法をレビュー。UI と追加 OAuth は利用需要が出てから実装 |

P0 のソース変更は `patches/mori.patch` と `overlay/` に記録する。生成 `.runtime/` を最終ソースとして編集しない。個別の窓・メニュー・保存移行テストを追加し、Node 24.18+ のルート `npm test`、通常ランタイム再構築、現在のランタイム保持と次回起動ソース一致を別々に確認する。窓の重なり、タスクバー、DPI、ドラッグは Windows 実機で受け入れる。
