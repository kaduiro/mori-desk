# Calendar・Gmail HUD の実装と本番受入計画

作成日: 2026-11-04（Asia/Tokyo）。[UX と複数アカウントの設計案](calendar-mail-ux-and-account-roadmap-ja.md)、[残存タスク](../remaining-tasks-20261105-ja.md)、[Gmail 社内導入条件](../mail/gmail-hud-deployment-ja.md)を統合した実行計画。この文書は計画であり、下記のソース変更・法人環境での操作を完了したという記録ではない。

## 前提と達成条件

- 個人検証では A/B の Gmail 同期と、両アカウントにログインした Chrome での各 HUD リンク到達を確認した。試験後の Mori Desk は A に再連携済み。本番の組織所有 Cloud プロジェクト、管理者承認、法人パイロットは未着手。
- 本番は社員の所属する Google Workspace / Cloud Identity 組織が所有するプロジェクトを使う。Calendar と Gmail の既存コードは認証・データ領域が別なので、本番でも API と Desktop OAuth クライアントを分ける。組織の管理要件に応じて Cloud プロジェクトも別々にする案を第一候補とする。
- 通常起動はブラウザー中心のまま。HUD の改善で CLI 設定・既存のブラウザー連携・Google トークンを暗黙に変更しない。メール・予定の内容はログや検証記録へ転記しない。
- 完了とは、ソース実装、通常ランタイム再構築、ルート回帰テスト、Windows 実機受入、法人管理者による Cloud/OAuth 条件確認、法人先行利用までを指す。macOS に配る場合は同 OS の実機受入と署名を追加する。

## 第1段階: HUD の操作性を実装する

| 順 | ソース変更 | 実装の要点 | 完了条件 |
| --- | --- | --- | --- |
| 1 | `patches/mori.patch` の main メニュー context と `src/menu.js` のトレイ・キャラクターメニュー | `openMoriMail` を既存の `moriBrowserWindow.openMail()` へ結び、両メニューに「受信メール」を追加。ブラウザー専用起動時の `workGroup.splice(2)` をやめ、CLI 専用項目だけ条件追加する | 未連携でも設定導線付きの Mail HUD を開け、連携済みなら一覧へ一操作で戻る。Calendar・ブラウザ連携・CLI 有効時の既存項目も残る |
| 2 | 新規の純粋な配置計算モジュールを `overlay/src/` に置き、`mori-calendar-window.js` と `mori-mail-window.js` から利用 | ペット・作業領域・他 HUD の位置を入力し、両 HUD が可能な範囲で重ならない初期位置を返す。手動で移動した窓は動かさない。画面変更時は見える領域へ収める | 2つを同時に自動表示しても、一般的な画面サイズで片方がもう片方を覆わない。複数モニター・DPI 変更後も操作可能 |
| 3 | 両 window モジュールの `BrowserWindow` 設定と各 `layout.json` | `resizable: true`、タスクバーから復帰できる設定へ変更。例: 初期 `400×480`、最小 `320×300`。バージョン1の `x/y` を読めるまま、バージョン2では `x/y/width/height` を保存。数値・画面範囲を検証し、保存に失敗しても表示は継続 | サイズ変更・移動・再起動・解像度変更後に使える位置とサイズに復元。既存の位置設定を失わない |
| 4 | `mori-calendar.css`、`mori-mail.css`、両 HTML/renderer | 標準文字14px程度、補足・時刻12px以上を基準とし、文字倍率 `100/125/150%` を選べるようにする。固定 px 指定を整理し、拡大時は件名と時刻を折り返す。一覧と詳細のスクロール領域、ボタンの操作面積を確保 | 両 HUD の本文・日時・詳細・設定が倍率変更後も読め、横切れせず操作できる。窓拡大のみを文字改善の代わりにしない |
| 5 | 両 window モジュールの表示ライフサイクル | 手動のメニュー起動は `show()` と `focus()`、自動起動は `showInactive()` を使い分ける。通常のフォーカス喪失では閉じない。明示的な「×」、他窓の背面化、DND 等による一時抑制を別状態にする。自動表示が抑制された場合の表示意図を保持し、解除時に復帰する。ユーザーが閉じた窓は自動復帰しない | 他アプリを押しても HUD が失われず、タスクバーまたは右クリックから戻れる。DND・ミニ・HUD 無効・ペット非表示と手動表示の現行境界を維持 |

「クリックすると消える」現象は、現時点でコードに `blur` → `hide()` は見当たらず、実際の原因が未確定。第5項の変更前に Windows 実機で `isVisible`、`isFocused`、`blur`、`hide`、`closed` と抑制理由を状態種別・回数だけで確認する。初期位置で両 HUD がほぼ重なること、現在の `skipTaskbar: true`、手動 Calendar 再表示がフォーカスしないことはソースで確認済み。診断に件名・本文・URL・アドレスを含めない。メール本文は明示的な終了と抑制による窓破棄時にメモリから消す。

実装テストは、メニューの CLI 無効・有効両分岐、旧レイアウトからの移行、範囲外座標の補正、両 HUD の衝突回避、手動/自動/明示閉鎖/抑制の遷移を個別アサーションで確認する。窓の重なり、タスクバー表示、サイズ変更、倍率、フォーカスは Windows 実機で合否を決める。枠なし透明窓の端を OS がリサイズできるかも実機で確かめ、操作が分かりにくければ目印または代替のサイズ選択 UI を加える。

## 第2段階: 個人環境で機能受入を終える

| 対象 | 手順 | 合格条件 |
| --- | --- | --- |
| Calendar 実予定 | 既存または本人が用意した当日予定で、複数カレンダーの一覧、説明文、会議参加 URL、時刻順、詳細の開閉を確認 | 最新の予定が正しいカレンダー・時刻で現れ、詳細の URL が当該予定を指す。本文・URL は証跡に書かない |
| Calendar 継続表示 | ペットと HUD のドラッグ、他アプリのクリック、HUD を閉じて再表示、アプリ再起動、OS ログイン起動、日付切替を確認 | 位置・サイズ・文字倍率が保持され、再同意なしで当日分に更新。前日の予定を当日として残さない |
| 抑制・障害 | DND、ミニモード、HUD 無効、オフライン、更新連打を確認 | 自動表示だけを抑制し、手動表示は可能。失敗時は取得済みデータと最終取得時刻を明示し、過剰な API 呼び出しをしない |
| Gmail 詳細・更新 | 優先送信者の追加・削除、その他未読との区分、本文の遅延表示、URL、手動更新、「さらに読み込む」を確認 | 優先・その他が重複せず受信時刻順。設定を開いても一覧が操作可能。初回100件を超える未読の範囲を明示 |
| Gmail のアカウント指定リンク | 利用対象の Chrome で、A/B 両ログイン、アクティブ Gmail の切替、ログイン順の逆転、対象アカウントだけが未ログインの条件を確認 | URL が示すアカウントの対象メールだけを開く。対象が未ログインなら別アカウントのメールを開かずログイン案内になる。Chrome で失敗例があれば深いリンクを配布可とせず、詳細画面のアカウント・件名による手動確認導線へ切り替える |

Google ログイン状態を変える試験は、日常用 Chrome を壊さないよう独立した Chrome プロファイルまたは検証用環境で行う。Brave や IAB の結果は Chrome 限定の合否判定に用いない。実 Gmail の閲覧で既読が変わる場合は、試験対象を事前に選び、終了後に元の状態を確認する。

## 第3段階: 法人の Google Cloud と OAuth を準備する

この段階は組織所有の本番プロジェクトと権限を持つ管理者が必要であり、個人検証用プロジェクトを本番へ流用しない。Google の現在の資料では、Gmail `gmail.readonly` は制限付きスコープ、組織所有プロジェクトの Internal 利用は OAuth 審査の例外条件に入り得る。ただし組織管理者によるアクセス制御が必要になり得る。複数組織や個人 Gmail の社員へ配るなら Internal だけを前提にせず、審査要件を別途判断する。[スコープ](https://developers.google.com/workspace/gmail/api/auth/scopes)、[Internal の条件](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification)、[組織のアプリ制御](https://knowledge.workspace.google.com/admin/apps/control-which-apps-access-google-workspace-data)。

1. **所有と対象者**: IT 管理者が社員の所属組織、利用対象の組織部門、プロジェクト所有者、OAuth 同意画面の Internal 設定可否を確定する。Internal は同組織全体を対象にするため、30人など限定配布には管理コンソール側の組織部門・アプリ制御を別に決める。
2. **プロジェクトとクライアント**: 組織所有の Calendar/Gmail 用プロジェクトを分ける案を基本とし、Calendar は `calendar.events.readonly` と `calendar.calendarlist.readonly`、Gmail は `gmail.readonly` に限定する。各プロジェクトで API を有効化し、Desktop OAuth client を発行する。システムブラウザー、PKCE、ループバック応答を維持し、ドメイン全体の代理権限は使わない。[Desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app)。
3. **管理者承認**: 管理コンソールでクライアント ID と要求スコープ、対象組織部門を確認する。必要なら `Specific Google data` で必要スコープだけを許可する案を優先し、全スコープを許す `Trusted` を安易に選ばない。承認者・日付・根拠・拒否時の表示を記録する。[管理コンソールの選択肢](https://knowledge.workspace.google.com/admin/apps/control-which-apps-access-google-workspace-data)。
4. **実利用枠と課金**: Cloud Console の各本番プロジェクトで、ユーザー/分、プロジェクト/分、24時間閾値、Cloud Billing の紐付けと請求先を実測し、証跡を残す。Gmail の現行公開値は 6,000 units/ユーザー/分、1,200,000 units/プロジェクト/分、80,000,000 units/プロジェクト/24時間の課金閾値だが、2026-05-01 以降の枠変更とプロジェクトごとの実効値を優先する。[Gmail 利用枠](https://developers.google.com/workspace/gmail/api/reference/quota)。Calendar の標準利用は現時点で追加料金なしとされ、将来の課金変更予定があるため導入時に再確認する。[Calendar 利用枠と料金](https://developers.google.com/workspace/calendar/api/guides/quota)。
5. **予算と監視**: 予算通知の受信者、通知閾値、API 使用量・429/403・同期遅延の確認担当を決める。通知だけの予算は支出を自動停止しない。[Cloud Billing の予算](https://docs.cloud.google.com/billing/docs/how-to/budgets)。ローカルの Gmail 上限は端末あたり20,000 units/24時間・2,500 units/分だが、ユーザーの複数 PC や他アプリの同一プロジェクト利用は合算されるため、本番 Cloud 側の監視が必要。

Gmail は現行の5分差分確認と「更新」を維持する。Google はデスクトップなどユーザー所有デバイスの更新取得にはポーリング同期を推奨しており、Pub/Sub を必須にしない。[Gmail push の説明](https://developers.google.com/workspace/gmail/api/guides/push)。概算は社員数 `N`、1人1日の新着 `M`、本文詳細を開く回数 `D`、手動更新 `R` として `N × (576 + 20M + 60D + 2R)` units/日、初回100件に約2,005 units/人を追加する。実測の履歴変更件数・再試行を含めて Cloud メトリクスと照合する。30台が各20,000 unitsのローカル上限まで使っても Mori の合計は最大約600,000 units/24時間だが、同一プロジェクトの他の利用を含まず、費用を保証する値ではない。

## 第4段階: 法人先行試験と配布判定

1. 管理者が認めた1～2人の法人アカウントで、社内用クライアント・同意画面・要求スコープ・初回同期・更新・詳細・再起動を確認する。拒否や失効時はデータが混ざらず、理由を利用者へ示す。
2. 7～14日を目安に少人数の Windows PC で、Calendar の日付切替と Gmail の新着、5分更新、手動更新、ローカル/Cloud の利用量とエラーを観察する。診断は状態・件数だけとし、個人の予定・メール内容を収集しない。
3. 実装担当とは独立したレビューで、OAuth と `safeStorage`、IPC の送信元・ID 検証、外部 URL、HUD の一時非表示時の本文破棄、API 台帳と再試行を確認する。UI の変更でメールや予定の内容が診断へ混入しないことも確認する。
4. 対象 OS 向けの実ビルド、署名、OS 信頼、インストール・再起動・更新・アンインストールを検証する。未作成のバイナリを利用可能と表現しない。個人用 OAuth JSON・更新トークン・キャッシュを配布物へ含めない。
5. 合否表に、HUD の再表示と文字の可読性、リンクのアカウント一致、Calendar の実予定、同期遅延、実利用枠・課金状態、管理者承認、回帰テスト、既知の未確認項目を記録する。リンクが別アカウントへ誤遷移する場合は深いリンクと URL コピーを社内向けに提供せず、手動確認導線を完成してから再判定する。

ソース変更後は `patches/mori.patch` と `overlay/` を最終成果とし、生成物 `.runtime/` は直接コミットしない。Node 24.18+ の `npm test` で個々のアサーションと終了状態を確認し、`npm run rebuild` で通常ランタイムを再構築する。従前の利用可能なランタイムが保持されたことと、次回起動の `source_check_passes/source_matches` を別々に記録する。

| Workspace / Cloud 管理者 | 組織所有のプロジェクト作成権限、対象社員・組織部門の確定 | プロジェクト所有、Internal 対象、OAuth クライアントと許可スコープ、管理者承認の記録 |

第1段階のソース作業と個人受入は本番プロジェクトがなくても着手できる。第3・4段階は組織の権限と法人アカウントが揃うまで完了にできない。社内配布の判定では、個人検証の成功を法人環境の成功として代用しない。

## 今回は設計のみとする複数 Gmail アカウント

当面は1アカウント・1 Mail HUD を維持する。将来追加するときは、認証・暗号化キャッシュ・優先送信者・非表示 ID・同期状態を不透明な `accountId` に分離し、行識別子と IPC の参照を `(accountId, messageId)` にする。端末の API 台帳は共有しつつユーザー別使用量を把握し、1件の OAuth 解除が他アカウントを消さないようにする。1つの HUD の切替方式と複数 HUD 方式は、実需要と利用者試験で選ぶ。既存の単一アカウント保存形式の移行を UX 改善と同時に実行しない。
